# 应用层协议

## 应用层概述与两种模型

应用层是体系结构中的最高层，直接为用户的应用进程提供服务。应用层协议定义了运行在不同端系统上的应用进程如何相互交换报文，具体规定交换报文的类型（如请求报文与响应报文）、各种报文类型的语法（报文中有哪些字段及各字段如何描述）、字段的语义（字段中信息的含义）以及进程何时、如何发送报文以及对报文进行响应的规则。应用层的许多协议都是基于客户/服务器（C/S）方式的：客户是服务请求方，服务器是服务提供方，服务器具有固定的 IP 地址与熟知端口，总是处于打开状态，客户则主动发起通信。另一种模型是对等连接（P2P）方式：通信双方在对等连接中并不区分哪一方是服务请求方、哪一方是服务提供方，每个结点既可作为客户请求服务，也可作为服务器提供服务，其优点是具有良好的可扩展性，能够充分利用边缘结点的带宽与存储资源，典型应用如 BitTorrent、区块链网络。

## DNS 的域名结构

DNS（域名系统）是互联网使用的命名系统，用来把便于人们使用的机器名字转换为 IP 地址。互联网采用层次树状结构的命名方法：任何一个连接在互联网上的主机或路由器都有一个唯一的层次结构名字，即域名。域名的结构由标号序列组成，各标号之间用点隔开，如 www.example.com.cn，其中越靠右的标号级别越高。域名空间自顶向下依次为：根（用点表示，通常省略）、顶级域名、二级域名、三级域名等。顶级域名分为三类：国家顶级域名，如 cn 表示中国、us 表示美国、uk 表示英国；通用顶级域名，如 com 表示公司企业、net 表示网络服务机构、org 表示非营利组织、edu 表示教育机构、gov 表示政府部门、int 表示国际组织、mil 表示军事部门；新通用顶级域名，如 aero、biz、info、name、pro、museum、xyz 等。域名只是一个逻辑概念，它并不反映主机所在的物理位置，一台主机可以更换 IP 地址而保持域名不变。

## 域名服务器的分类

域名到 IP 地址的解析由分布在互联网上的域名服务器完成，DNS 采用层次结构的分布式数据库，主要分为四类域名服务器。根域名服务器是最高层次的域名服务器，也是最重要的服务器，所有根域名服务器都知道所有的顶级域名服务器的域名与 IP 地址；全球共有 13 个根域名服务器逻辑标识（编号 a 到 m），通过任播技术在全球部署了大量镜像实例。顶级域名服务器负责管理在该顶级域名下注册的所有二级域名。权限域名服务器负责管理某个区的域名，每个区（zone）设置相应的权限域名服务器，区可能小于或等于一个域，当一个权限域名服务器还不能给出最后的查询回答时，就会告诉查询者下一步应当找哪一个权限域名服务器。本地域名服务器并不属于上述层次结构，它通常是 ISP 或单位内部的 DNS 服务器，当一个主机发出 DNS 查询请求时，这个查询请求报文就发送给本地域名服务器，由它代为进行后续查询，因此本地域名服务器也称为默认域名服务器。

## 递归查询与迭代查询

DNS 查询有两种方式。主机向本地域名服务器的查询一般采用递归查询：如果本地域名服务器不知道被查询域名的 IP 地址，那么本地域名服务器就以 DNS 客户的身份向其他根域名服务器继续发出查询请求报文，而不是让主机自己进行下一步查询，最终把查询结果返回给主机。本地域名服务器向根域名服务器的查询通常采用迭代查询：当根域名服务器收到本地域名服务器的迭代查询请求报文时，要么给出所要查询的 IP 地址，要么告诉本地域名服务器下一步应当向哪一个域名服务器进行查询，然后让本地域名服务器进行后续的查询，而不代替它继续查询。例如查询 www.example.com 时，本地域名服务器先问根服务器，根服务器告知".com 顶级域名服务器的地址"；本地域名服务器再问该顶级域名服务器，得到 example.com 权限域名服务器的地址；再问权限域名服务器，最终得到 www.example.com 的 IP 地址。整个过程中主机只发出一次递归查询，本地域名服务器则发出多次迭代查询。递归查询对发起方简单但对服务器负担重，迭代查询对服务器负担轻但要求发起方具备继续查询的能力。

## DNS 缓存与传输方式

为了提高 DNS 查询效率并减轻根域名服务器的负荷，减少互联网上的 DNS 查询报文数量，域名服务器与主机中都广泛使用高速缓存。高速缓存存放最近查询过的域名以及从何处获得域名映射信息的记录。当客户请求查询时，若本地域名服务器的高速缓存中已有该域名的映射信息，就直接把结果返回给客户，而不必再向其他服务器查询。由于域名到 IP 地址的映射并非永久不变，为保证高速缓存中的内容正确，域名服务器应为每项内容设置计时器并处理超过合理时间的项，当计时器到期时就删除该项，从而适应网络的变化。不仅是本地域名服务器使用高速缓存，主机也维护自己的 DNS 缓存（操作系统与浏览器各有一层）。此外，DNS 主要使用 UDP 进行查询与响应，服务器端口为 53，因为查询报文通常很短且要求快速响应；当响应报文长度超过 512 字节，或者进行区域传送（在主域名服务器与辅助域名服务器之间同步数据）时，则使用 TCP 的 53 端口以保证可靠传输。

## DNS 资源记录

DNS 数据库中存储的资源记录（RR）是域名解析的基本数据单元，每条资源记录是一个四元组：名称（Name）、值（Value）、类型（Type）、生存时间（TTL）。常见类型包括：A 记录，名称是主机名，值是 IPv4 地址，用于把域名解析为 IPv4 地址；AAAA 记录，名称是主机名，值是 IPv6 地址；CNAME 记录，名称是别名，值是规范主机名，用于给主机设置别名，使多个域名指向同一台主机；MX 记录，名称是邮件服务器的别名，值是邮件服务器的规范主机名，用于电子邮件系统，MX 记录还带有优先级字段，数值越小优先级越高；NS 记录，名称是域，值是该域的权限域名服务器的主机名，用于指出该域由哪台服务器负责解析；PTR 记录，用于反向域名解析，把 IP 地址解析为域名；SOA 记录，标识一个区的起始授权信息，包含主服务器、管理员邮箱、序列号、刷新间隔等；TXT 记录，用于存放文本信息，常用于域名所有权验证与 SPF 反垃圾邮件配置。理解资源记录类型有助于配置 DNS 与排查解析故障。

## WWW 与 URL

万维网（WWW）是一个大规模的、联机式的信息储藏所，它并非某种特殊的计算机网络，而是一个基于超文本与超媒体的信息系统。万维网的核心组成部分包括：统一资源定位符（URL），用于标识与定位万维网上的各种文档；超文本传输协议（HTTP），用于实现万维网上各种超链的链接与文档的传送；超文本标记语言（HTML），用于描述文档的结构与显示方式。URL 的一般格式为：协议://主机:端口/路径?查询字符串#片段标识符。其中协议指明访问方式，常见有 http、https、ftp、file 等；主机是域名或 IP 地址；端口在省略时使用协议的默认端口（HTTP 为 80，HTTPS 为 443）；路径指明资源在服务器上的位置；查询字符串以问号开始，由若干"参数名=参数值"对组成并用 & 分隔，用于向服务器传递参数；片段标识符以井号开始，指向文档内部的某个位置，它只在客户端使用，不会被发送到服务器。URL 中的主机名需要经 DNS 解析为 IP 地址，端口决定了与服务器哪个进程通信。

## HTTP 的请求报文格式

HTTP 报文分为请求报文与响应报文两类，均采用纯文本的 ASCII 编码，便于阅读与调试。请求报文由四部分组成：请求行、首部行（若干行）、空行（CRLF）、实体主体（可选）。请求行由三个字段组成，用空格分隔：方法字段、URL 字段、HTTP 版本字段，例如"GET /index.html HTTP/1.1"。首部行采用"首部字段名: 值"的格式，每行一个字段，常见请求首部包括 Host（指明请求的主机名与端口，HTTP/1.1 中必需）、User-Agent（用户代理，标识浏览器类型）、Accept（可接受的媒体类型）、Accept-Language、Accept-Encoding（可接受的压缩编码）、Connection（如 keep-alive 或 close）、Cookie（携带客户端保存的 Cookie）、Referer（来源页面）、Content-Type 与 Content-Length（在携带实体时说明类型与长度）。空行用于分隔首部与实体主体，即使没有实体主体，空行也不能省略，服务器正是通过空行判断首部结束。实体主体通常只在 POST、PUT 等方法中出现。

## HTTP 的响应报文与状态码

响应报文同样由状态行、首部行、空行与实体主体组成。状态行由三个字段组成：HTTP 版本、状态码、原因短语（如"HTTP/1.1 200 OK"）。常见响应首部包括 Server（服务器软件信息）、Date（生成响应的时间）、Content-Type（实体主体的媒体类型，如 text/html、application/json）、Content-Length、Content-Encoding、Last-Modified、ETag、Set-Cookie（要求客户端保存 Cookie）、Cache-Control、Location（配合重定向使用）。状态码为三位数字，分为五类：1xx 表示信息性状态码，表示请求已接收、继续处理；2xx 表示成功，如 200 OK 表示请求成功、204 No Content 表示成功但无返回内容、206 Partial Content 表示返回部分内容（用于断点续传）；3xx 表示重定向，如 301 Moved Permanently 永久移动、302 Found 临时移动、304 Not Modified 表示资源未修改（配合条件 GET 使用缓存）；4xx 表示客户端错误，如 400 Bad Request 请求语法错误、401 Unauthorized 未认证、403 Forbidden 无权限、404 Not Found 资源不存在；5xx 表示服务器错误，如 500 Internal Server Error 服务器内部错误、502 Bad Gateway 网关错误、503 Service Unavailable 服务不可用。

## HTTP 的常用方法

HTTP 定义了一组请求方法，用以表明对资源的操作意图。GET 是最常用的方法，用于请求读取由 URL 标识的资源，参数通常放在 URL 的查询字符串中，可被缓存与收藏。HEAD 与 GET 类似，但服务器只返回响应首部而不返回实体主体，常用于检查资源是否存在、是否被修改以及获取元信息。POST 用于向指定资源提交数据，数据放在实体主体中，常用于表单提交、文件上传与创建资源，不可缓存且不幂等。PUT 用于向服务器上传资源并在指定位置创建或替换，是幂等的。DELETE 用于请求服务器删除指定资源，也是幂等的。PATCH 用于对资源进行部分修改。OPTIONS 用于查询服务器支持的请求方法或进行跨域预检。TRACE 用于回显服务器收到的请求，便于诊断。CONNECT 用于要求服务器建立隧道，常用于 HTTPS 代理。所谓幂等是指执行一次与连续执行多次的效果相同，GET、HEAD、PUT、DELETE、OPTIONS 是幂等的，POST 与 PATCH 通常不是。理解方法的语义对设计 RESTful 接口与排查问题都很重要。

## 持久连接与非持久连接

HTTP 连接分为非持久连接与持久连接。在非持久连接方式下，每个请求/响应都通过一个单独的 TCP 连接完成，服务器发送响应后即关闭连接。以获取一个包含 1 个 HTML 基础文件与 10 个内嵌对象的页面为例，采用非持久连接且串行请求时需要建立 11 个 TCP 连接，每个连接要经历三次握手，因此总时间包含多个 RTT，效率很低；即使使用并行连接（浏览器通常对同一域名并行打开 4~6 个连接），开销仍然显著。HTTP/1.0 默认使用非持久连接，可通过 Connection: keep-alive 请求持久连接。在持久连接方式下，服务器发送响应后仍保持 TCP 连接打开，同一客户对同一服务器的后续请求与响应都在这个连接上发送，从而省去了重复建立连接的开销、降低了时延并减轻了服务器负担。HTTP/1.1 默认使用持久连接（流水线式持久连接），可通过 Connection: close 显式要求关闭。持久连接分为流水线方式与非流水线方式：流水线方式允许客户在收到前一个响应之前就发出下一个请求，但服务器必须按序响应，且存在队头阻塞问题。HTTP/2 通过多路复用、首部压缩与二进制分帧进一步改进了这一机制。

## Cookie 与 Web 缓存

HTTP 本身是无状态协议，服务器不保存客户的任何信息，这简化了服务器设计但无法支持需要识别用户身份的场景。Cookie 技术用于在无状态的 HTTP 之上维护用户状态，它由四个部分组成：服务器在响应报文中通过 Set-Cookie 首部行给客户发送一个唯一的识别码；客户的浏览器在本地 Cookie 文件中保存该识别码与该服务器的对应关系；此后客户向该服务器发送的每个请求都在 Cookie 首部行中携带该识别码；服务器后端数据库根据该识别码识别用户，从而提供个性化服务或维持登录状态。Cookie 可设置有效期（会话 Cookie 在关闭浏览器后失效，持久 Cookie 保存在磁盘上）、作用域（域名与路径）以及 HttpOnly、Secure、SameSite 等安全属性。Web 缓存（代理服务器）是另一项提高性能的技术：代理服务器代表浏览器保存最近请求过的对象的副本，当再次收到对同一对象的请求时，若副本未过期则直接返回，从而减少响应时间、减少机构出口链路上的流量。为验证缓存是否仍然有效，HTTP 使用条件 GET 机制：缓存向服务器发送带 If-Modified-Since 或 If-None-Match 的请求，若资源未变则服务器返回 304 Not Modified，不携带实体主体。

## HTTPS 与 TLS 握手流程

HTTPS 就是在 HTTP 与 TCP 之间加入 TLS/SSL 安全层，使用 443 端口，提供机密性、完整性与服务器身份认证。其核心是混合加密体制：用非对称加密安全地协商出一个会话密钥，再用对称加密高效地保护实际数据。TLS 1.2 的完整握手流程大致为：客户端发送 ClientHello，包含支持的 TLS 版本、密码套件列表与一个客户端随机数；服务器回应 ServerHello，选定 TLS 版本与密码套件并给出服务器随机数，随后发送 Certificate 报文（服务器的数字证书链）、ServerKeyExchange（若使用临时密钥交换算法则发送密钥交换参数与签名）、ServerHelloDone；客户端验证证书是否由受信任的 CA 签发、域名是否匹配、是否在有效期内，然后发送 ClientKeyExchange（用服务器公钥加密的预主密钥，或基于 Diffie-Hellman 的客户端参数），双方根据两个随机数与预主密钥通过伪随机函数导出会话密钥；客户端发送 ChangeCipherSpec 通知后续报文将被加密，再发送 Finished（包含之前所有握手报文的摘要，用于验证握手未被篡改）；服务器同样发送 ChangeCipherSpec 与 Finished。此后双方使用会话密钥进行对称加密通信。TLS 1.3 大幅简化了握手，只需 1 个 RTT 即可完成，并支持会话恢复时的 0-RTT。

## FTP 协议

FTP（文件传输协议）用于在网络上进行文件传输，它使用客户/服务器方式，一个 FTP 服务器进程可同时为多个客户进程提供服务。FTP 的独特之处在于它使用两条并行的 TCP 连接：控制连接与数据连接。控制连接始终保持打开，用于传输客户与服务器之间的命令与响应，服务器端口为 21；数据连接用于实际传送文件内容，在每次传输文件时建立、传输结束后关闭。FTP 使用控制连接在带外传送控制信息，因此把控制信息与数据分离，这种设计称为带外控制。FTP 有两种工作模式：主动模式（PORT），服务器用自己的 20 端口主动连接客户指定的数据端口，客户需要开放端口，在客户位于 NAT 或防火墙之后时容易失败；被动模式（PASV），客户向服务器请求一个临时端口，由客户主动连接该端口建立数据连接，对客户端更友好，是实际使用中的常见模式。FTP 的数据传输模式可指定为 ASCII 模式（用于文本文件，会自动转换换行符）或二进制模式（用于程序与压缩文件）。FTP 的登录需要用户名与密码，也支持匿名登录。

## 电子邮件系统与 SMTP

电子邮件系统由用户代理、邮件服务器与邮件协议三部分构成。用户代理（UA）是用户与电子邮件系统的接口，即运行在用户计算机上的邮件客户端软件，负责撰写、显示、处理与收发邮件。邮件服务器是电子邮件系统的核心，负责邮件的发送与接收，并负责向发件人报告交付结果，它需要全天候运行并维护用户邮箱（实际上是服务器磁盘上为用户开设的一块存储空间）。邮件协议主要有发送邮件用的 SMTP 与读取邮件用的 POP3、IMAP。SMTP（简单邮件传输协议）使用 TCP 连接，端口为 25，采用客户/服务器方式：发送方邮件服务器作为 SMTP 客户，接收方邮件服务器作为 SMTP 服务器。SMTP 通信有三个阶段：连接建立、邮件传送、连接释放；常用命令有 HELO/EHLO、MAIL FROM、RCPT TO、DATA、QUIT，响应以三位数字状态码开头。SMTP 只能传送 7 位 ASCII 码文本，因此需要用 MIME（多用途互联网邮件扩展）对非 ASCII 数据（如中文、图像、附件）进行编码转换，MIME 并非取代 SMTP，而是在其基础上增加了邮件主体的结构定义与编码规则。

## POP3 与 IMAP

POP3（邮局协议第 3 版）与 IMAP（互联网消息访问协议）都是用于用户从邮件服务器读取邮件的协议，采用客户/服务器方式与拉（pull）模式，与 SMTP 的推（push）模式正好相反。POP3 使用 TCP 110 端口，其工作过程分为授权、事务处理与更新三个阶段：授权阶段用户发送用户名与密码进行认证；事务处理阶段用户可列出邮件、下载邮件、标记删除邮件；更新阶段在用户执行 QUIT 后服务器才真正删除被标记的邮件。POP3 的显著特点是"下载并删除"模式：邮件一旦被用户代理下载到本地就从服务器删除，因此用户在不同设备上看到的邮件不一致，且服务器存储压力小。IMAP 使用 TCP 143 端口，功能更强：邮件始终保存在服务器上，用户代理可以在服务器上创建文件夹、移动邮件、按部分读取邮件（如只读取正文而不下载大附件）、搜索邮件并维护已读/未读等标志状态。IMAP 适合在多设备间同步邮件的现代使用习惯，但需要更多服务器存储与处理资源。基于 TLS 的版本分别为 POP3S（995）与 IMAPS（993）。

## 电子邮件的工作流程

一封电子邮件的完整发送与接收过程可分解为几个步骤。第一步，发件人使用用户代理撰写邮件，填写收件人地址（格式为 用户名@邮件服务器域名），用户代理把邮件交给发送方邮件服务器，此过程可使用 SMTP（现代邮件客户端提交邮件常用 587 端口的 SMTP Submission）或厂商私有协议。第二步，发送方邮件服务器把邮件放入发送队列，作为 SMTP 客户尝试与接收方邮件服务器的 25 端口建立 TCP 连接。第三步，若发送成功，接收方邮件服务器把邮件放入收件人的用户邮箱，等待收件人读取；若发送失败（如对方服务器不可达或地址不存在），发送方邮件服务器会定期重试，超过一定次数后放弃并向发件人返回差错报告。第四步，收件人通过用户代理使用 POP3 或 IMAP 连接到接收方邮件服务器，认证后下载或在线读取邮件。这里的关键点是：发送邮件使用 SMTP，接收方从服务器读取邮件使用 POP3 或 IMAP；发送方用户代理到发送方服务器可以用 SMTP，也可以使用其他协议；而两台邮件服务器之间始终使用 SMTP 通信。DNS 中的 MX 记录用于查出收件人域对应的邮件服务器。

## 一次完整网络访问的流程

从在浏览器地址栏输入一个网址到页面最终显示，涉及整个协议栈的协同工作。第一步，浏览器解析 URL，提取协议、主机名、端口与路径，并检查浏览器缓存与系统 DNS 缓存。第二步，若缓存中没有该域名的 IP 地址，则进行 DNS 解析：主机向本地域名服务器发递归查询，本地域名服务器依次向根、顶级与权限域名服务器发迭代查询，最终获得 IP 地址并逐级缓存。第三步，主机判断目的 IP 是否与本机在同一网段：若不在，则需把数据交给默认网关，此时通过 ARP 解析网关的 MAC 地址（ARP 请求广播、响应单播，结果写入 ARP 缓存）。第四步，与服务器建立 TCP 连接，进行三次握手；若使用 HTTPS，则在此基础上进行 TLS 握手，协商会话密钥并验证服务器证书。第五步，浏览器发送 HTTP 请求报文，服务器返回响应报文（状态码、首部与实体主体）。第六步，浏览器解析 HTML，遇到内嵌的 CSS、图片、脚本等资源时再次发起请求并渲染。第七步，页面加载完毕后，若不用持久连接则通过四次挥手释放连接（主动关闭方进入 TIME-WAIT 并等待 2MSL）。整个过程体现了分层与封装解封装：HTTP 报文被逐层封装成 TCP 报文段、IP 数据报与以太网帧，到达对端后再逐层解封装。
