# UDP 与传输层基础

## 传输层的功能

传输层向上面的应用层提供通信服务，是面向通信部分的最高层，也是面向用户功能的最低层。它承担三项基本功能。第一，传输层提供应用进程之间的端到端逻辑通信：网络层提供的是主机到主机的通信，即数据报只被送到目的主机，而一台主机上可能同时运行多个应用进程，把数据交给哪一个进程是网络层无法解决的，必须由传输层通过端口机制来区分。第二，传输层对上层屏蔽下层网络的细节：网络层之下的通信子网在拓扑、技术、速率上差异极大，传输层使应用进程看到的是一个统一的、逻辑上的端到端通道。第三，传输层提供复用与分用功能，并可根据需要提供可靠传输、流量控制与拥塞控制。由于传输层处于用户功能与通信功能的交界处，它的实现完全位于端系统的主机中，路由器只需实现到网络层为止，这是互联网"端到端原则"的体现。

## 进程之间的通信

网络通信的实质是应用进程之间的通信。当两台主机通过互联网通信时，真正需要交换数据的是运行在各自主机上的进程。例如主机 A 上的浏览器进程要与主机 B 上的 Web 服务器进程通信，数据需要依次经过 A 的应用层、传输层、网络层、数据链路层与物理层，经中间路由器转发到 B，再反向经过 B 的各层到达 B 的服务器进程。从传输层的角度看，通信的实体是进程，而通信的端点是两个主机中的进程；从网络层的角度看，通信的实体是主机。这两个视角的差异正是传输层存在的理由：网络层只能把数据送到主机，而传输层负责把数据交付给正确的进程。因此，传输层协议必须提供一种机制来标识通信的双方进程，这种机制就是端口号。需要注意的是，两台主机之间的通信实际上是由多个进程之间的通信复用在同一条物理链路上完成的，这体现了分层思想带来的抽象与复用。

## 端口与端口号

端口（port）是传输层为标识应用进程而引入的抽象概念，端口号是一个 16 位的整数，取值范围是 0~65535。传输层使用端口号来标识本主机中的应用进程，因此端口号只具有本地意义，即端口号只是为了标识本计算机应用层中的各进程，不同计算机中的相同端口号是没有关联的。IP 地址标识了互联网上的主机，端口号标识了主机中的进程，二者结合（IP 地址 + 端口号）才能唯一确定互联网中的一个通信端点。在 TCP/IP 协议栈中，端口号分为三类：熟知端口号（系统端口号），范围 0~1023，由 IANA 统一分配给最重要的应用协议，如 FTP 用 21、SSH 用 22、Telnet 用 23、SMTP 用 25、DNS 用 53、HTTP 用 80、POP3 用 110、HTTPS 用 443；登记端口号，范围 1024~49151，供没有熟知端口号的应用程序使用，需在 IANA 登记；客户端口号（短暂端口号），范围 49152~65535，留给客户进程在运行时临时选择使用。

## 端口号的常见分配

为便于学习与配置，应记住常见协议的端口号分配。使用 TCP 的应用协议及其端口：FTP 数据连接 20、控制连接 21，SSH 22，Telnet 23，SMTP 25，HTTP 80，POP3 110，IMAP 143，HTTPS 443，BGP 179，LDAP 389，RDP 3389。使用 UDP 的应用协议及其端口：DNS 53，DHCP 服务器 67 与客户 68，TFTP 69，SNMP 161 与 SNMP Trap 162，RIP 520，NTP 123。需要特别说明的是，DNS 主要使用 UDP 端口 53，因为域名查询通常是短报文且要求快速响应；但当响应报文超过 512 字节或进行区域传送时则改用 TCP 53。端口号的作用范围是本主机，因此不同主机上相同端口号的服务互不干扰。服务器进程通常在熟知端口上"收听"连接请求，客户端则从短暂端口号范围内随机选择一个作为源端口，从而形成唯一的连接四元组。

## 套接字

套接字（socket）是传输层通信的端点，由 IP 地址与端口号组合而成，通常写作"IP 地址:端口号"，例如 192.168.1.10:8080。在 TCP 通信中，一条连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识，因此连接的两个端点各是一个套接字。套接字是应用进程与传输层之间的编程接口，操作系统提供了一组称为套接字 API 的系统调用，包括 socket（创建套接字）、bind（绑定本地地址与端口）、listen（进入收听状态，仅服务器使用）、accept（接受连接，仅服务器使用）、connect（发起连接，仅客户端使用）、send/recv 或 write/read（收发数据）、close（关闭连接）等。服务器端的典型流程是 socket → bind → listen → accept → recv/send → close；客户端的典型流程是 socket → connect → send/recv → close。理解套接字概念有助于把协议原理与编程实践联系起来，也有助于理解连接四元组如何唯一确定一条 TCP 连接。

## 复用与分用

复用与分用是传输层的核心机制。复用是指在发送方，多个应用进程的数据都可以通过同一个传输层协议、使用同一条网络层的 IP 通道发送出去，也就是把多个进程的数据汇聚到一条链路上传输。分用是指在接收方，传输层根据报文段首部中的端口号，把收到的数据正确地交付给对应的应用进程。分用分为两种情形：在无连接的 UDP 中，UDP 根据目的端口号把用户数据报交给相应的进程，若该端口没有进程在监听则丢弃并回送 ICMP 端口不可达报文；在面向连接的 TCP 中，分用需要根据四元组查找对应的连接控制块，因为同一端口上可能同时存在多条连接（如 Web 服务器 80 端口上的成千上万条连接），只有四元组才能唯一确定是哪一条连接的数据。复用与分用使得一台主机能够同时运行多个网络应用，而不会互相干扰，这是现代操作系统网络栈的基础功能。

## UDP 的特点

UDP（用户数据报协议）只在 IP 的数据报服务之上增加了很少一点功能，即复用分用与差错检测，因此具有以下特点。第一，UDP 是无连接的，发送数据之前不需要建立连接，因此没有连接建立与释放的时延开销。第二，UDP 使用尽最大努力交付，即不保证可靠交付，因此主机不需要维持复杂的连接状态表，也不需要确认与重传机制。第三，UDP 是面向报文的，发送方的 UDP 对应用层交下来的报文既不合并也不拆分，而是保留这些报文的边界：应用层交给 UDP 多长的报文，UDP 就照样发送，即一次发送一个报文；接收方 UDP 对每个报文也是原样交付，一次交付一个完整报文。因此应用层必须选择合适的报文长度，若报文太长，IP 层分片会降低效率并增加丢失风险；若报文太短，首部开销比例过高。第四，UDP 没有拥塞控制，因此网络出现拥塞时源主机不会降低发送速率，这对实时应用很重要，但也可能导致网络更加拥塞。第五，UDP 支持一对一、一对多、多对一和多对多的交互通信。第六，UDP 首部开销小，只有 8 字节。

## UDP 首部格式

UDP 用户数据报的首部由 4 个字段组成，每个字段 2 字节，共 8 字节。源端口占 2 字节，在需要对方回信时选用，不需要时可用全 0。目的端口占 2 字节，在终点交付报文时必须使用。长度占 2 字节，指 UDP 用户数据报的长度，即首部与数据部分的总长度，其最小值为 8（只有首部而无数据）。检验和占 2 字节，用于检测 UDP 用户数据报在传输中是否出现差错，若检验和有差错则直接丢弃该数据报，不做任何处理。UDP 首部之后就是数据字段，其长度由应用层报文长度决定。由于首部固定为 8 字节且没有可变部分，UDP 的处理非常简单快速，这也是它时延小的原因之一。与 TCP 相比，UDP 首部没有序号、确认号、窗口、标志位等字段，因此它无法实现可靠传输、流量控制与拥塞控制，这些功能只能由应用层自行实现或在应用层协议中补充。

## UDP 校验和与伪首部

UDP 的检验和计算方式较为特殊：在计算检验和时，需要在 UDP 用户数据报之前临时增加 12 字节的伪首部，它既不向下传送也不向上递交，只是为了计算检验和而临时构造的。伪首部包含四个字段：源 IP 地址（4 字节）、目的 IP 地址（4 字节）、全 0 字段（1 字节）、协议字段（1 字节，UDP 的值为 17）、UDP 长度（2 字节）。增加伪首部的目的是让接收方能够检查 UDP 用户数据报是否在两个正确的端点之间传送，即检验 IP 地址与协议号是否正确，从而防止数据被错误交付。检验和的计算方法是：把伪首部、UDP 首部与数据部分一起按 16 位字进行反码算术求和，再把结果取反码写入检验和字段；若计算结果为全 0，则把检验和字段置为全 1（即 0xFFFF），以避免与"不进行检验和计算"的情形混淆。UDP 的检验和是可选的，若不使用则置为 0，但由于伪首部的参与使检验能覆盖 IP 地址，通常建议启用。当数据部分长度不是偶数个字节时需要补一个全 0 字节参与计算，但不发送该字节。

## UDP 的适用场景

UDP 适合以下几类应用场景。第一类是实时性要求高、能容忍少量丢包的应用，如 IP 电话、视频会议、在线游戏，这类应用宁可有少量数据丢失也不愿因重传导致时延抖动。第二类是简单请求-响应模式的短报文应用，如 DNS 查询、DHCP、SNMP、TFTP，使用 UDP 可以省去连接建立与释放的开销，响应更快。第三类是需要广播或多播的应用，如局域网内的服务发现、流媒体多播，因为 TCP 只支持一对一通信，无法直接实现多播。第四类是由应用层自行实现可靠性与拥塞控制的应用，如 QUIC、部分游戏协议，它们利用 UDP 的简单性获得对传输行为的完全控制，避免内核 TCP 的僵化与协议僵化问题。第五类是承载大量并发短事务的服务，如图 5G 核心网中的部分信令。相对地，需要保证数据完整、按序到达且不怕时延的应用（如文件传输、网页浏览、电子邮件、远程登录）应使用 TCP。

## TCP 与 UDP 的比较

TCP 与 UDP 的主要区别可以从多个维度列出。连接性：TCP 面向连接，需要三次握手建立、四次挥手释放；UDP 无连接，直接发送。可靠性：TCP 提供可靠交付，通过序号、确认、重传保证无差错、不丢失、不重复、按序到达；UDP 尽最大努力交付，可能丢失、重复、失序。数据形式：TCP 面向字节流，不保留应用层报文边界；UDP 面向报文，保留边界。通信方式：TCP 只支持一对一；UDP 支持一对一、一对多、多对一、多对多。首部开销：TCP 最小 20 字节；UDP 固定 8 字节。传输效率与实时性：TCP 有流量控制与拥塞控制，速率自适应，时延与吞吐波动较大；UDP 没有这些机制，时延小且稳定，但可能加剧网络拥塞。适用协议：TCP 用于 HTTP/HTTPS、FTP、SMTP、POP3、IMAP、SSH、Telnet、BGP；UDP 用于 DNS、DHCP、TFTP、SNMP、RIP、NTP、实时音视频。选择的依据是对可靠性与实时性的权衡：既要可靠又要实时时，通常需要在应用层自行设计折中方案。

## 套接字编程接口

应用层通过套接字接口使用传输层的服务，接口有两种主要风格：基于字节流的流式套接字（SOCK_STREAM）对应 TCP，基于数据报的套接字（SOCK_DGRAM）对应 UDP。流式套接字的服务器端典型调用序列为：socket 创建套接字，bind 绑定 IP 与端口，listen 把套接字变为被动收听状态并设置连接队列长度，accept 阻塞等待客户连接并返回一个新的已连接套接字（注意监听套接字与已连接套接字是两个不同的描述符）；随后用 recv/send 或 read/write 收发数据，最后 close 关闭。客户端序列为 socket、connect、send/recv、close。由于 TCP 面向字节流，一次 send 的数据可能被拆成多次 recv 收到，或多次 send 的数据被合并成一次 recv，因此应用层必须自己处理报文边界，这正是"粘包"问题的根源。数据报套接字的服务器只需 socket 与 bind，然后用 recvfrom/sendto 收发，每次调用对应一个完整的数据报，不需要监听与接受连接。

## 基于 UDP 的现代传输协议

随着网络发展，直接在 UDP 之上构建传输协议成为一种重要趋势。HTTP/3 使用 QUIC 作为传输层，而 QUIC 正是基于 UDP 实现的。这样做的主要动机有三点：一是避开内核 TCP 的僵化，TCP 由操作系统内核实现且中间设备（防火墙、NAT、负载均衡器）对其行为有诸多假设，改进 TCP 需要漫长的标准化与部署周期，而在用户态基于 UDP 实现协议可以快速迭代；二是解决队头阻塞问题，TCP 的字节流语义使一个报文段丢失会阻塞后续所有数据的交付，而 QUIC 在一条连接上复用多个独立的流，单个流的丢包不影响其他流；三是把加密与握手结合，QUIC 把 TLS 1.3 集成到握手中，实现 0-RTT 或 1-RTT 建连，显著降低首包时延。QUIC 还在用户态实现了自己的可靠传输、拥塞控制（如 CUBIC、BBR）、连接迁移（使用连接 ID 而非四元组标识连接）等功能，是传输层演进的重要方向。

## 传输层的安全与 TLS

传输层本身不提供加密功能，TCP 与 UDP 的数据在网络上以明文传输，任何中间结点都可以窃听或篡改。为了解决这一问题，出现了在传输层与应用层之间插入安全子层的做法，最典型的是 TLS（传输层安全协议，其前身是 SSL）。TLS 位于 TCP 之上、应用协议之下，为 HTTP、SMTP、FTP 等提供机密性、完整性与身份认证：机密性通过对称加密（如 AES）实现，密钥由握手阶段协商；完整性通过消息认证码（如 HMAC）或带关联数据的认证加密（AEAD）实现；身份认证通过数字证书与公钥基础设施（PKI）实现，服务器出示由 CA 签名的证书，客户端验证证书链以确认服务器身份。使用 TLS 的 HTTP 即 HTTPS，默认端口 443。由于 TLS 需要有序可靠的字节流，它传统上运行在 TCP 之上；而在 QUIC 中，TLS 1.3 被集成进 QUIC 的握手过程，运行在 UDP 之上。这与 TLS 在协议栈中的位置变化，体现了安全功能与传输功能日益融合的趋势。
