# TCP 可靠传输与流量控制

## TCP 的特点

TCP（传输控制协议）是传输层面向连接的、可靠的传输协议。其主要特点包括：TCP 是面向连接的协议，应用进程在使用 TCP 之前必须先建立连接，数据传输结束后必须释放连接；TCP 提供点对点（一对一）的服务，每条 TCP 连接只能有两个端点，因此不支持广播与多播；TCP 提供可靠交付的服务，通过序号、确认、重传、流量控制与拥塞控制等机制保证数据无差错、不丢失、不重复且按序到达；TCP 提供全双工通信，连接的双方都设有发送缓存与接收缓存，可以同时向对方发送数据；TCP 是面向字节流的，它把应用进程交下来的数据看成是一连串无结构的字节流，而不保留应用层报文的边界。面向字节流意味着 TCP 不关心应用层一次交付多少数据，它在发送时可以根据网络状况对字节流进行切分与合并，因此接收端的一次读操作可能只得到半个应用层报文，应用层必须自行处理报文边界。

## TCP 报文段首部格式（固定字段）

TCP 报文段首部的前 20 字节是固定的，后面可以有可变长度的选项，因此首部最小为 20 字节、最大为 60 字节。固定字段依次为：源端口与目的端口各占 2 字节，共 4 字节，加上 IP 首部的源与目的 IP 地址就唯一确定了一条连接（四元组）；序号占 4 字节；确认号占 4 字节；数据偏移（首部长度）占 4 位，单位为 4 字节，指出 TCP 首部的长度，最小取 5；保留字段占 6 位，目前置为 0；然后是 6 个标志位，共 6 位；窗口占 2 字节；检验和占 2 字节；紧急指针占 2 字节。这 20 字节之后再接选项字段与填充。理解每个字段的位置与单位，是分析 TCP 行为与解决计算题的基础。

## TCP 序号与确认号

序号字段占 4 字节（32 位），由于 TCP 是面向字节流的，序号的值不是报文段的编号，而是本报文段所发送的数据的第一个字节的序号，取值范围为 0~2³² − 1。TCP 连接建立时，双方各自随机选择一个初始序号（ISN），而不是固定从 0 或 1 开始，这样可以避免旧连接中延迟到达的报文段被误认为是本次连接的合法数据，从而增强安全性。确认号字段占 4 字节，表示期望收到对方下一个报文段的第一个数据字节的序号，因此若确认号为 N，则表明到序号 N − 1 为止的所有数据都已正确收到。例如接收方收到一个报文段，其中序号为 201、数据长度为 100 字节（字节 201~300），则接收方回送的确认号为 301，同时把窗口值更新后一并返回。确认号只有在 ACK 标志位为 1 时才有效；连接建立后所有传送的报文段都必须把 ACK 置为 1。

## TCP 首部的标志位与其他字段

TCP 首部有 6 个标志位，各占 1 位，用于表达控制信息。紧急 URG：当 URG = 1 时，表明紧急指针字段有效，表示报文段中有紧急数据，应尽快传送。确认 ACK：仅当 ACK = 1 时确认号字段才有效；TCP 规定连接建立后所有报文段都必须把 ACK 置为 1。推送 PSH：当 PSH = 1 时，接收方应尽快把数据交给应用进程，而不必等整个缓存填满。复位 RST：当 RST = 1 时，表明 TCP 连接出现严重差错（如崩溃、拒绝非法连接），必须释放连接后重新建立。同步 SYN：SYN = 1 表示这是一个连接请求或连接接受报文，用在三次握手中。终止 FIN：FIN = 1 表示发送方数据已发送完毕，要求释放连接。此外，窗口字段占 2 字节，指出从本报文段的确认号开始，接收方还能接收多少字节的数据，用于流量控制；检验和占 2 字节，计算时需要加上 12 字节的伪首部；紧急指针占 2 字节，指出本报文段中紧急数据的字节数。

## TCP 的选项字段

TCP 首部的可变部分即选项字段，其长度由数据偏移字段决定，最长可到 40 字节。常见选项包括：最大报文段长度（MSS），在连接建立时由双方在 SYN 报文中通告，表示本方能接受的报文段数据部分的最大长度，它只计入数据部分而不包含首部，以太网环境下 MSS 通常取 1460 字节（1500 减 20 字节 IP 首部再减 20 字节 TCP 首部）；窗口扩大选项，因为基本首部的窗口字段只有 16 位，最大只能表示 65535 字节，在长肥管道（高带宽长时延链路）上不足以充分利用带宽，该选项通过指定一个移位值把窗口字段左移若干位，从而把最大窗口扩大到 2³⁰ 字节量级；选择确认（SACK）选项，允许接收方指出已收到的不连续字节块，使发送方只需重传真正缺失的部分，避免不必要的重传；时间戳选项，用于更精确地测量往返时间并防止序号回绕带来的混淆。选项字段的长度必须是 4 字节的整数倍，不足时用填充补齐。

## TCP 面向字节流与报文段划分

TCP 把应用进程交付的数据看作连续的字节流，并为每个字节编号。发送方并不保留应用层报文的边界，而是根据当前允许的发送窗口大小、路径 MTU 与拥塞窗口状况决定如何切分字节流。例如应用进程连续交付了两个分别为 100 字节和 50 字节的应用层报文，TCP 可以把它们合并成一个 150 字节数据部分的报文段发送，也可以先发 40 字节、再发 110 字节，接收方按序号重组后交付给应用进程。因此 TCP 的接收方无法从到达的报文段判断应用层报文边界，必须由应用层协议自行定义边界方式：定长报文、以特定分隔符结束（如 HTTP 首部的换行）、或在报文首部中给出长度字段（如 HTTP 的 Content-Length 与分块传输编码）。这也解释了为什么在 TCP 编程中需要处理"粘包"与"拆包"问题。此外，发送方应尽量避免发送过小的报文段，以免首部开销比例过高，Nagle 算法就是为此设计的。

## TCP 可靠传输：序号与确认机制

TCP 实现可靠传输的核心是序号与确认机制。TCP 在发送数据时，为每个字节编上序号；接收方正确收到数据后回送确认，确认号表示期望收到的下一个字节的序号。由于 TCP 连接是全双工的，双方都可以发送数据与确认，因此 TCP 的确认可以捎带在发往对方的数据报文段中，即"捎带确认"，这样可以减少报文数量、提高效率。若接收方暂时没有数据要发送，则单独发送一个只有首部而无数据的确认报文段。TCP 规定，确认号 N 表示"序号 N − 1 及以前的所有字节都已正确收到"，这种确认方式称为累积确认。累积确认的优点是实现简单、确认开销小，且即使某个确认报文段丢失，后续的确认也可以补救；缺点是无法精确告知发送方哪些数据已收到、哪些没有收到，当出现不连续到达时发送方可能重传已经收到的数据，这正是引入选择确认（SACK）选项的原因。

## 累积确认

累积确认是 TCP 确认机制的基本形式：接收方收到序号连续的数据后，只对按序到达的最后一个字节之后的那个序号进行确认，而不必为每个报文段单独发送确认。例如发送方依次发送字节 1~100、101~200、201~300 三个报文段，若全部正确到达，接收方只需发送确认号 301 的一个确认（也可以为每个报文段分别发送确认号 101、201、301，但通常延迟确认以合并）。若中间报文段丢失，例如 101~200 丢失而 201~300 到达，接收方不能把 201~300 交付应用层（因为必须按序交付），它仍然只能重复发送确认号 101，这类重复的确认称为重复确认。发送方连续收到多个确认号相同的重复确认，就可能推断出报文段丢失并触发快速重传。累积确认的关键性质是：确认号只会向前推进，不会后退；收到一个确认号较大的确认，等价于确认了此前所有字节。这也意味着延时确认（通常延迟 200 ms 或在收到两个报文段后立即确认）可以与捎带确认配合，显著减少确认报文数量。

## 超时重传与 RTT 估计

超时重传是 TCP 可靠性的基础机制：发送方为每个已发送但未确认的报文段设置计时器，若在超时时间 RTO 内没有收到确认，就重传该报文段。RTO 的设置至关重要：设置过小会导致不必要的重传，加重网络负担；设置过大会导致丢包后等待过久，传输效率低下。由于 RTT 随网络状况不断变化，TCP 采用自适应算法估计。记 RTT 的一次测量值为 RTT 样本，则：首次测量时，加权平均往返时间 RTTS 取该样本值，偏差 RTTD 取样本值的一半；此后每次测得新样本，按 RTTS ← (1 − α) × 旧 RTTS + α × 新样本（推荐 α = 1/8），RTTD ← (1 − β) × 旧 RTTD + β × |RTTS − 新样本|（推荐 β = 1/4）更新，最后取 RTO = RTTS + 4 × RTTD。这种估计使 RTTS 平滑地跟踪 RTT 的变化趋势，而 RTTD 反映了 RTT 的波动程度，RTO 随波动自动放大，从而在稳定链路上保持较小超时、在抖动链路上避免过度重传。

## Karn 算法

在使用超时重传时，会出现 RTT 样本的歧义问题：当发送方重传了某个报文段后收到确认，这个确认究竟是对原始报文段的确认还是对重传报文段的确认？如果误把重传时刻当作起点计算 RTT 样本，将得到一个偏小的样本值，导致 RTTS 与 RTO 被低估，进而引发更多不必要的重传。Karn 算法给出了解决规则：在计算加权平均往返时间 RTTS 时，只要报文段被重传过，就不采用该报文段的往返时间样本。这一规则避免了歧义，但带来另一个问题：当网络状况恶化导致大量重传时，由于不再有新的样本，RTO 无法更新。为此 Karn 算法配合另一条规则使用：报文段每重传一次，就把 RTO 增大一些，典型做法是取新的 RTO = γ × 旧的 RTO（γ 通常取 2），即超时时间按指数规律退避。当不再发生重传时，再根据新的往返时间样本重新计算 RTO。这一机制与以太网的二进制指数退避思想类似，都是为了在网络拥塞时降低发送速率。

## 快速重传

超时重传的缺点是等待时间较长，可能导致传输停顿，为此 TCP 引入了快速重传机制。其依据是：当接收方收到失序到达的报文段时，会立即重复发送对最后一个按序字节的确认，从而产生重复确认。发送方若连续收到 3 个对同一序号的重复确认（即收到 3 个重复 ACK），就认为该序号之后的那个报文段已经丢失，于是不必等待计时器超时，立即重传该报文段。选择 3 这个数字是一种折中：网络中的乱序到达也可能产生一两个重复确认，若数量太小会误判为丢包并触发不必要的重传；若太大则反应过慢。快速重传与快速恢复配合使用，可以在出现个别丢包时避免把拥塞窗口降为 1、重新从慢开始，从而保持较高的吞吐量。当重复确认的数量不足以判定丢包时，仍需依靠超时重传作为最后保障。

## TCP 流量控制与滑动窗口

TCP 的流量控制通过滑动窗口机制实现，目的是让发送方的发送速率不超过接收方的接收能力，防止接收缓存溢出导致数据丢失。接收方在返回的每个确认报文段中，利用首部的窗口字段通告自己的接收窗口 rwnd，即从确认号开始还能接收的字节数；发送方把自己的发送窗口设置为不超过 rwnd，并据此控制发送。发送窗口内的字节分为四类：已发送并已收到确认的字节（可移出窗口）、已发送但未收到确认的字节、未发送但可发送的字节（可用窗口）、未发送且超出窗口的字节。每收到一个确认，窗口就向前滑动。发送方实际可发送的数据量还受拥塞窗口的限制，因此发送窗口的实际取值为发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)。TCP 是全双工的，连接的每一端都同时维护发送窗口与接收窗口，双方都可能成为"发送方"或"接收方"，因此各自都需要进行流量控制。

## 零窗口与持续计时器

当接收方的接收缓存已被填满而上层应用进程尚未读取数据时，接收方会把窗口字段置为 0 并发送出去，这就是零窗口通告，表示发送方应暂停发送。发送方收到零窗口通告后停止发送数据，但这里存在一个死锁风险：如果接收方随后腾出空间，会发送一个非零窗口的通告，而该通告报文一旦丢失，发送方将一直等待非零窗口通告，接收方则一直等待发送方发送数据，双方陷入永久等待。为解决这一问题，TCP 为发送方设置了持续计时器：当发送方收到零窗口通告时，就启动持续计时器；计时器到期后，发送方主动发送一个零窗口探测报文段（只含 1 字节数据或不含数据），接收方收到探测后必须给出当前的窗口值。若窗口仍为 0，则发送方重置持续计时器继续等待；若窗口已增大，则发送方可以继续发送数据。持续计时器使零窗口状态下的连接自动恢复，避免了死锁。TCP 的持续计时器超时时间通常采用指数退避方式增长。

## 糊涂窗口综合症与 Nagle 算法

糊涂窗口综合症是指发送方与接收方在交互过程中传输大量小报文段，使有效数据传输效率极低的现象。它有两种表现形式：一是发送方每收到一个确认就发送一个很小的报文段，即使可用窗口很小；二是接收方每腾出一点缓存空间就通告一个小窗口，诱使发送方发送小报文段。假设每个报文段首部开销为 40 字节而数据只有 1 字节，则传输效率仅为约 2.4%。解决办法分别从两端入手。发送方采用 Nagle 算法：若发送方要发送的数据不足一个 MSS，则先发送第一个字节，把其余数据缓存起来，等到收到确认或积累到一个 MSS 时再发送。接收方采用延迟确认与窗口等待策略：不要在缓存刚有一点空间时就通告小窗口，而是等缓存能容纳一个 MSS 的空间或缓存空间达到总容量的一半时，再通告一个较大的窗口。两种策略配合使用，可以有效抑制小报文段的产生，显著提高链路利用率。

## 发送窗口的实际取值

TCP 的发送窗口并非单一因素决定，而是由流量控制与拥塞控制共同约束。设接收方通告的接收窗口为 rwnd，发送方维护的拥塞窗口为 cwnd，则发送窗口的上界为 min(rwnd, cwnd)。换言之，发送方在任意时刻已发送但尚未收到确认的字节数，不能超过接收方的接收能力，也不能超过网络当前的承载能力。当网络没有拥塞时，cwnd 通常较大，发送窗口由 rwnd 决定，此时限制来自接收方；当网络出现拥塞、cwnd 收缩到很小时，发送窗口由 cwnd 决定，限制来自网络。此外，报文段长度还受 MSS 与路径 MTU 的约束。这三个量的叠加关系可以形象地记为"发送窗口 = min(接收窗口, 拥塞窗口)"，这是 TCP 流量控制与拥塞控制两大机制的交汇点，也是分析 TCP 吞吐量问题时最常使用的公式。TCP 的吞吐量近似等于发送窗口除以往返时间 RTT。

## TCP 与 UDP 的比较概览

TCP 与 UDP 是传输层的两个主要协议，它们的差异源于设计目标的不同。TCP 面向连接、提供可靠交付、面向字节流、支持一对一通信、首部最小 20 字节、有流量控制与拥塞控制、传输速率自适应且时延波动较大，适合对正确性要求高的应用。UDP 无连接、尽最大努力交付、面向报文、支持一对一/一对多/多对多交互、首部仅 8 字节、无流量控制与拥塞控制、时延小且稳定，适合实时性与广播类应用。需要澄清一个常见误解：UDP 并非"不可靠"就毫无用处，它把可靠性交给应用层自行决定，从而获得更低的时延与更简单的实现；而 TCP 的可靠性是以额外的确认、重传开销与更复杂的连接管理为代价的。在具体应用中，文件传输、电子邮件、网页浏览使用 TCP；域名解析、实时音视频、网络管理、IP 电话多使用 UDP，部分现代协议（如 QUIC、HTTP/3）则基于 UDP 自行实现可靠传输。
