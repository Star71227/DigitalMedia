# TCP 连接管理与拥塞控制

## TCP 连接的本质

TCP 连接并不是一条真正的物理链路，而是一种逻辑连接，它只存在于通信双方主机的传输层中。TCP 把连接作为最基本的抽象，每条连接由四元组唯一标识：源 IP 地址、源端口号、目的 IP 地址、目的端口号。只要四元组中有一项不同，就是不同的连接，因此同一台服务器可以在同一端口上同时与成千上万个客户建立连接。TCP 连接的两个端点称为套接字（socket），即 IP 地址与端口号的组合。连接建立后，双方各自维护连接的状态信息，包括发送缓存、接收缓存、发送窗口、接收窗口、拥塞窗口、各类计时器以及序号与确认号的当前值，这些信息由操作系统内核维护。由于连接由内核维护，连接状态必须在双方同时存在才能工作，因此 TCP 需要一套严格的状态机来管理连接的建立与释放。

## 三次握手的过程

TCP 建立连接的过程称为三次握手。第一次握手：客户进程主动打开连接，向服务器发送连接请求报文段，其中同步位 SYN = 1，同时选择一个初始序号 seq = x，此时报文段不携带数据但消耗一个序号；客户进入 SYN-SENT（同步已发送）状态。第二次握手：服务器收到请求后，若同意连接，则发回连接接受报文段，其中 SYN = 1、ACK = 1，确认号 ack = x + 1，同时为自己选择一个初始序号 seq = y；服务器进入 SYN-RCVD（同步收到）状态。第三次握手：客户收到服务器的报文段后，向服务器发送确认报文段，其中 ACK = 1，确认号 ack = y + 1，序号 seq = x + 1，该报文段可以携带数据；客户与服务器都进入 ESTABLISHED（连接已建立）状态。三次握手完成后，双方都确认了对方的存在，并且都同步了初始序号，连接正式建立，可以开始全双工数据传输。第三次握手的确认报文段如果不携带数据则不消耗序号。

## 为什么需要三次握手

采用三次握手而不是两次握手，最根本的原因是为了防止已失效的连接请求报文段突然又传送到服务器，从而造成服务器资源的浪费。设想一种异常情形：客户发出的某个连接请求报文段在网络中长时间滞留，未能按时到达服务器；客户超时后重传并成功建立连接、完成数据传输、正常释放连接；此后那个滞留在网络中的旧连接请求报文段才到达服务器。如果是两次握手，服务器收到该报文段后就认为新的连接已建立，于是分配资源并一直等待客户发送数据，而这个客户根本没有发起新连接，导致服务器资源被长期白白占用。采用三次握手后，服务器在收到旧的连接请求后发出确认并进入 SYN-RCVD 状态，但客户不会对这个从未发起过的连接发送第三次确认，服务器在超时后就会释放该半开连接，资源不会被浪费。此外，三次握手也让双方都能确认对方的接收能力和初始序号，保证序号同步的可靠性。

## 三次握手中序号与标志位的变化

三次握手中，序号与确认号的变化规律是分析问题的关键。设客户选择的初始序号为 x，服务器选择的初始序号为 y。第一次握手报文段携带 seq = x、SYN = 1、ACK = 0；第二次握手报文段携带 seq = y、ack = x + 1、SYN = 1、ACK = 1；第三次握手报文段携带 seq = x + 1、ack = y + 1、ACK = 1、SYN = 0。需要特别注意 SYN 与 FIN 标志位各消耗一个序号，而普通确认报文段若不携带数据则不消耗序号，因此第三次握手的报文段中序号仍为 x + 1 而不是 x + 2。若第三次握手的报文段携带了数据，则序号仍从 x + 1 开始，数据占用随后的序号，服务器的确认号将相应变为 x + 1 + 数据长度。如果双方同时主动打开连接，则会出现同时发送 SYN 的四次报文交换（称为同时打开），此时双方都经历 SYN-SENT → SYN-RCVD → ESTABLISHED 的过程。若客户发送 SYN 后未收到响应而超时，会按指数退避重传 SYN，重传次数达到上限则放弃并报错。

## 四次挥手的过程

TCP 释放连接的过程称为四次挥手，因为 TCP 连接是全双工的，每个方向必须单独关闭。第一次挥手：客户打算关闭连接，发送连接释放报文段，其中 FIN = 1，序号 seq = u（等于前面已传送数据的最后一个字节的序号加 1），此时客户进入 FIN-WAIT-1（终止等待 1）状态。第二次挥手：服务器收到 FIN 后发出确认，ACK = 1，确认号 ack = u + 1，序号 seq = v，此时服务器进入 CLOSE-WAIT（关闭等待）状态，客户收到确认后进入 FIN-WAIT-2（终止等待 2）状态。此时从客户到服务器方向的连接已关闭，但服务器到客户方向的连接仍然存在，服务器仍可继续发送数据，这种状态称为半关闭状态。第三次挥手：当服务器把剩余数据全部发送完毕后，发送连接释放报文段，FIN = 1、ACK = 1，序号 seq = w，确认号 ack = u + 1，服务器进入 LAST-ACK（最后确认）状态。第四次挥手：客户收到服务器的 FIN 后必须发出确认，ACK = 1，确认号 ack = w + 1，序号 seq = u + 1，客户进入 TIME-WAIT（时间等待）状态，服务器收到后进入 CLOSED 状态，客户经过 2 倍最长报文段寿命（2MSL）后也进入 CLOSED 状态。

## 为什么挥手需要四次

挥手的四次交互源于 TCP 的全双工特性以及 FIN 与数据发送的独立性。当客户发送 FIN 时，它只表示"我这一方向没有数据要发送了"，并不表示服务器也没有数据要发送。服务器收到 FIN 后，TCP 协议栈会立即回复一个 ACK，因为确认是传输层自动完成的；但服务器可能还有数据未发送完毕，或者应用进程尚未调用关闭操作，因此服务器不能立即发送 FIN。这样 ACK 与 FIN 就必须分两次发送，于是总共有四次报文交换。如果服务器在收到 FIN 时恰好也没有数据要发送，它可以把 ACK 与 FIN 合并在一个报文段中发送，此时看起来只有三次交互，但协议语义上仍属于四次挥手的流程。另一种情况是双方同时关闭连接，各自发送 FIN，则每一方都经历 FIN-WAIT-1、CLOSING、TIME-WAIT 的过程，这种情况称为同时关闭，需要交换四个报文段。理解这一点有助于分析实际抓包中出现的各种报文序列。

## TIME-WAIT 与 2MSL

主动关闭连接的一方在发送最后一个 ACK 后进入 TIME-WAIT 状态，必须等待 2MSL（Maximum Segment Lifetime，报文段最大生存时间）后才能进入 CLOSED 状态。等待 2MSL 有两个理由。第一，保证最后一个 ACK 能够到达服务器：如果这个 ACK 丢失，服务器会超时重传 FIN，此时客户仍处于 TIME-WAIT 状态，可以重新发送 ACK；若客户立即关闭，则服务器将永远收不到确认，无法正常释放连接。等待 2MSL 恰好覆盖"一个 FIN 重传加上一个 ACK"的最长时间。第二，防止旧连接的延迟报文段干扰新连接：在 2MSL 时间内，本次连接产生的所有报文段都会从网络中消失，这样在随后建立的、恰好使用相同四元组的新连接中，就不会收到旧连接的过期报文段，从而避免数据混乱。MSL 在 RFC 中建议为 2 分钟，实际实现中常取 30 秒、60 秒或更短，因此 TIME-WAIT 通常持续 1~4 分钟。在高并发服务器上大量 TIME-WAIT 会占用端口与内存资源，可通过开启 TIME-WAIT 重用与快速回收等参数缓解，但需权衡安全风险。

## TCP 状态转换

TCP 连接的完整生命周期可用状态转换图描述，主要状态包括：CLOSED（关闭）、LISTEN（收听，服务器等待连接请求）、SYN-SENT（同步已发送）、SYN-RCVD（同步收到）、ESTABLISHED（连接已建立，数据可双向传送）、FIN-WAIT-1（终止等待 1）、FIN-WAIT-2（终止等待 2）、CLOSE-WAIT（关闭等待）、CLOSING（关闭中，用于同时关闭）、LAST-ACK（最后确认）、TIME-WAIT（时间等待）。客户与服务器的路径并不对称：服务器经历 CLOSED → LISTEN → SYN-RCVD → ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED；主动关闭的客户经历 CLOSED → SYN-SENT → ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED。掌握状态转换图的实际意义在于运维排障：大量连接处于 SYN-RCVD 可能意味着遭受 SYN 洪泛攻击；服务器上大量 CLOSE-WAIT 往往说明应用程序没有正确关闭套接字；大量 TIME-WAIT 通常出现在高并发短连接的服务端；而 CLOSING 状态则提示发生了同时关闭。

## SYN 洪泛攻击与防范

SYN 洪泛攻击是典型的拒绝服务攻击。攻击者伪造大量源 IP 地址，向服务器端口发送 SYN 报文段。服务器对每个 SYN 都回复 SYN-ACK 并分配资源、进入 SYN-RCVD 状态，等待第三次握手的确认。由于源地址是伪造的，攻击者不会回复确认，服务器只能等到超时后才释放这些半连接。当攻击速率足够高时，服务器的半连接队列（SYN 队列）被占满，正常客户的连接请求无法被处理，服务因此不可用。常见防范措施包括：启用 SYN Cookie，服务器在收到 SYN 时不立即分配资源，而是把连接信息编码进自己的初始序号 y 中，只有在收到合法确认并验证 cookie 后才分配资源；缩短 SYN 超时时间并增大半连接队列容量，提高攻击门槛；启用 SYN 代理或首包丢弃机制，由中间设备代为完成握手验证；在网络边界部署防火墙、入侵检测与流量清洗设备，对来自单一来源的异常 SYN 速率进行限制；此外还可以通过调整内核参数（如开启 tcp_syncookies）实现软件层面的防护。

## TCP 拥塞控制概述

拥塞控制的目的是防止过多的数据注入网络，使网络中的路由器或链路不致过载。拥塞与流量控制不同：流量控制是针对接收方处理能力的端到端控制，拥塞控制是针对网络传输能力（路由器缓存与链路带宽）的全局性控制。拥塞控制是一个动态的、涉及全网的问题，仅靠增加路由器缓存并不能解决，反而可能因排队时延过大而加剧问题。TCP 拥塞控制采用"探测式"的方法：发送方维护一个拥塞窗口 cwnd，其大小取决于网络的拥塞程度并动态变化；发送方让发送窗口等于 min(rwnd, cwnd)。判断拥塞出现的依据是超时（未收到确认）或收到多个重复确认。TCP 的拥塞控制由四个算法共同完成：慢开始、拥塞避免、快重传与快恢复，它们由发送方根据网络状况切换使用。此外发送方还通过慢开始门限 ssthresh 来控制两种增长方式的切换：当 cwnd < ssthresh 时使用慢开始，当 cwnd > ssthresh 时使用拥塞避免，当二者相等时两者皆可。

## 慢开始

慢开始算法的思路是：当主机开始发送数据时，如果立即把大量数据注入网络，可能引起网络拥塞，因此应先探测网络的承载能力，由小到大逐渐增大发送窗口。具体规则是：在连接刚建立时，把拥塞窗口 cwnd 置为 1 个最大报文段长度（SMSS），即一个 MSS；每经过一个往返时间 RTT，cwnd 就加倍，因此 cwnd 按 1、2、4、8、16……的规律指数增长。实现上，每收到一个对新数据的确认，就把 cwnd 增加一个 MSS，这样在一个 RTT 内 cwnd 恰好翻倍。所谓"慢开始"并不是指 cwnd 的增长速率慢，而是指一开始发送的数据量少，增长速率实际上是指数级的、并不慢。为了防止 cwnd 增长过大引起网络拥塞，慢开始还设置了一个慢开始门限 ssthresh：当 cwnd 增长到 ssthresh 时，就改用拥塞避免算法。若某次加倍后 cwnd 超过 ssthresh，则通常把 cwnd 取为 ssthresh。在发生超时重传时，cwnd 会被重新置为 1 并再次执行慢开始。

## 拥塞避免

拥塞避免算法的思路是：让拥塞窗口 cwnd 缓慢增长，即每经过一个往返时间 RTT 只把 cwnd 增加 1 个 MSS，而不是像慢开始那样加倍。这样 cwnd 按线性规律增长，增长速度比慢开始慢得多，使网络不容易出现拥塞。实现上，每收到一个对新数据的确认，就把 cwnd 增加 MSS × MSS / cwnd（即按比例增加），使得在一个 RTT 内总共只增加约一个 MSS。无论是慢开始阶段还是拥塞避免阶段，只要发送方判断网络出现拥塞（其依据是没有按时收到确认，即发生了超时），就要把慢开始门限 ssthresh 设置为出现拥塞时的发送窗口值的一半（但不能小于 2 个 MSS），同时把拥塞窗口 cwnd 重新置为 1，然后重新执行慢开始算法。这种"乘法减小、加法增大"的组合策略使得 cwnd 在拥塞时迅速下降，在无拥塞时缓慢上升并在接近拥塞点附近长时间停留，从而在吞吐量与稳定性之间取得平衡。

## 快重传

快重传算法要求接收方不要等到自己发送数据时才进行捎带确认，而要立即发出确认，即使收到的是失序的报文段也要立即确认，以便让发送方尽早知道有报文段未能到达。快重传的具体规则是：发送方只要一连收到 3 个对同一报文段的重复确认，就立即重传对方尚未收到的报文段，而不必等到该报文段的重传计时器到期。之所以采用重复确认作为丢包信号，是因为报文段丢失会使后续到达的报文段序号不连续，接收方会反复确认缺失的那个序号，产生重复确认；而网络中的报文段乱序到达也可能产生少量重复确认，因此需要设定一个阈值。选择 3 个重复确认是一种折中：既能较快地发现真正丢失的报文段，又能避免因乱序而误判。快重传的意义在于不必等待超时，从而缩短了恢复时间，避免了因超时而把 cwnd 降为 1 所带来的吞吐量骤降。在实际抓包分析中，连续多个相同确认号的 ACK 是判断丢包的重要线索。

## 快恢复

快恢复算法与快重传配合使用。当发送方连续收到 3 个重复确认时，既然还能收到重复确认，就说明网络很可能并未严重拥塞（否则不会持续有报文到达），因此不必像超时那样把 cwnd 降为 1 并重新慢开始，而是执行快恢复：把慢开始门限 ssthresh 设置为当前发送窗口（或拥塞窗口）的一半，把拥塞窗口 cwnd 设置为新的 ssthresh 值，然后直接进入拥塞避免阶段，让 cwnd 按线性规律增长。部分实现（TCP Reno 的某些版本）在快恢复开始时把 cwnd 设为 ssthresh + 3 × MSS，以补偿已离开网络的 3 个重复确认所对应的报文段，随后每收到一个重复确认再把 cwnd 加 1，直到收到新数据的确认后把 cwnd 退回 ssthresh 并进入拥塞避免。与之对比，若丢包是由超时检测到的，则认为网络可能出现严重拥塞，此时 ssthresh = cwnd/2、cwnd = 1，并重新执行慢开始。

## 拥塞窗口与 ssthresh 的变化规律

综合四个算法，可以总结出 cwnd 与 ssthresh 的完整变化规律。连接建立初期，cwnd = 1、ssthresh 通常设为较大值（教材常取 16 个 MSS 以便说明），执行慢开始，cwnd 按 1、2、4、8、16 指数增长；当 cwnd 增大到 ssthresh 时改用拥塞避免，cwnd 按 17、18、19……线性增长。若在 cwnd = 24 时发生超时，则 ssthresh = 24/2 = 12，cwnd 重新置为 1，重新慢开始；此后 cwnd 按 1、2、4、8 增长，增长到 ssthresh（12）时改用拥塞避免，cwnd 按 13、14……线性增长。若在 cwnd = 16 时收到 3 个重复确认（而非超时），则执行快重传与快恢复：ssthresh = 16/2 = 8，cwnd = 8，直接进入拥塞避免，cwnd 按 9、10……线性增长，而不必回到 1。可以看出：超时使 cwnd 归 1 并重新慢开始，恢复缓慢；重复确认触发的快恢复只把 cwnd 减半，恢复较快。这就是"乘法减小、加法增大"的完整含义，也是解决 TCP 吞吐量计算题的核心依据。

## 主动队列管理与拥塞通知

TCP 的拥塞控制依赖端系统对丢包的判断，而路由器传统的尾部丢弃策略只有在缓存完全占满后才丢弃分组，此时已经产生了较大的排队时延。为更早地通知端系统降低发送速率，出现了主动队列管理（AQM）技术。随机早期检测（RED）是典型代表：路由器为队列长度设置两个门限，当平均队列长度小于最小门限时不丢弃；大于最大门限时全部丢弃；介于两者之间时按概率随机丢弃部分分组。随机丢弃使不同 TCP 连接的丢包时间错开，避免多个连接同时进入慢开始而造成全局同步，从而保持较高的链路利用率。另一种思路是显式拥塞通知（ECN）：路由器在队列即将溢出时，不丢弃分组，而是在 IP 首部的服务类型字段中置位，接收方通过 TCP 首部的相应标志位把拥塞信息回送给发送方，发送方象对待丢包一样减小 cwnd。ECN 避免了不必要的重传，对时延敏感业务更友好，现代数据中心网络广泛使用。

## TCP 的计时器

TCP 为每条连接维护多个计时器，共同保证协议的可靠运行。重传计时器：发送方每发送一个报文段就为该报文段启动，若在 RTO 内未收到确认则重传并将 RTO 加倍，收到确认后取消。坚持计时器：当发送方收到零窗口通告时启动，到期后发送零窗口探测报文段，以打破零窗口死锁。保活计时器：当连接长时间（通常 2 小时）没有数据交互时，服务器启动保活计时器，到期后发送探测报文段询问客户是否仍然在线，若连续多次无响应则释放连接，用于检测对端主机崩溃或链路中断的情况。时间等待计时器：在连接终止时设置，长度为 2MSL，用于保证最后一个 ACK 能送达并让旧报文段从网络中消失。此外，TCP 还使用延迟确认计时器（通常 200 ms）来合并确认、提高效率，以及使用持续重传计时器处理零窗口状态。理解这些计时器的作用有助于分析连接异常时的行为。
