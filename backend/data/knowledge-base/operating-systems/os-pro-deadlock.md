# 死锁

## 死锁的定义
死锁是指多个进程在运行过程中因争夺资源而造成的一种僵局：当进程处于这种僵持状态时，若无外力作用，它们都将无法向前推进。例如进程 P1 已占有资源 R1 并申请 R2，进程 P2 已占有 R2 并申请 R1，双方都在等待对方释放资源，于是永久阻塞。死锁产生于并发进程对不可剥夺资源的竞争，是一种与时间有关的错误，可能在某种执行顺序下才出现，因此难以发现和重现。可剥夺资源（如处理机、内存）不会引起死锁，只有不可剥夺资源（如打印机、磁带机、互斥锁）才可能引起死锁。

## 死锁、饥饿与死循环的区别
死锁是进程之间互相等待对方资源而形成的永久阻塞，参与死锁的进程数目至少为两个，必须借助外力（如撤销进程、剥夺资源）才能解除。饥饿（饿死）是指某进程由于调度策略不当而长期得不到所需资源，例如低优先级进程永远得不到处理机；饥饿的进程可能仍在等待队列中，只要有资源或策略改变就可能继续推进，且通常只涉及一个进程。死循环是程序逻辑错误导致的处理机重复执行同一段代码，它不涉及资源竞争，属于程序本身的问题。

## 产生死锁的四个必要条件
互斥条件：进程对所分配的资源进行排他性使用，即在一段时间内某资源只由一个进程占有。若不满足则不可能产生死锁。占有并等待条件（请求并保持）：进程已经保持了至少一个资源，但又提出了新的资源请求，而该资源已被其他进程占有，此时请求进程阻塞，但又对自己已获得的资源保持不放。不可剥夺条件：进程已获得的资源在未使用完之前不能被剥夺，只能在使用完后由自己释放。循环等待条件：存在一个进程—资源的循环等待链，链中每个进程已获得的资源同时被链中下一个进程所请求。四个条件必须同时成立才可能死锁，因此破坏其中任意一个即可预防死锁。

## 资源分配图
资源分配图用圆圈表示进程、方框表示资源（方框内的圆点表示该类资源的实例个数），从进程指向资源的边表示请求边，从资源指向进程的边表示分配边。若图中没有环路则系统一定不发生死锁；若图中存在环路，则是否死锁取决于资源的实例数：当每类资源只有一个实例时，环路是死锁的充分必要条件；当每类资源有多个实例时，环路只是死锁的必要条件而非充分条件，即环路存在时可能并不死锁。判断多实例情形是否死锁，可用资源分配图的化简方法：寻找既不阻塞又非孤立的进程结点（其请求都能被满足），消去其所有请求边与分配边使之成为孤立结点，若最终能消去所有边则图可完全简化，系统处于安全状态；否则存在死锁。

## 死锁处理策略概述
处理死锁有四类策略：死锁预防，通过破坏四个必要条件之一，使死锁在事先就不可能发生，代价是资源利用率降低；死锁避免，在资源分配之前用某种算法（如银行家算法）判断此次分配是否会导致系统进入不安全状态，只有安全时才分配；死锁检测与解除，允许死锁发生，通过定时检测发现死锁后再采取措施解除；忽略死锁（鸵鸟策略），不作任何处理，代价小但风险高。前两类属于事前预防，第三类属于事后处理。

## 死锁预防：破坏互斥条件
破坏互斥条件即允许多个进程同时使用原本互斥的资源，从而不存在"占有"的排他性。但这一条件是由资源本身的物理特性决定的，许多资源（如打印机、写文件、临界区）本质上不允许并发使用，因此通常无法破坏，这一策略的实用价值有限。可行的途径是尽量把独占设备改造为共享设备，例如用 SPOOLing 技术把打印机虚拟成共享设备，让多个进程的打印请求先写入磁盘缓冲区再依次输出，从而在逻辑上消除了对打印机的互斥竞争。

## 死锁预防：破坏占有并等待条件
破坏"占有并等待"有两种实现方式。第一种是静态分配（一次性分配全部资源）：进程在开始运行前一次性申请它所需的全部资源，若不能满足则一个资源也不占有并等待，由于运行期间不再申请新资源，故不可能出现"占有一部分又等待另一部分"的情形。第二种是资源在申请新资源之前先释放已占有的全部资源。这两种方式的共同缺点是资源利用率低，进程可能在开始前长时间等待，且由于需要预知所需资源的全部清单，实现起来有困难，还可能导致饥饿。

## 死锁预防：破坏不可剥夺条件
破坏不可剥夺条件即允许剥夺：一个已占有某些资源的进程再申请新资源而不能立即满足时，必须释放它已占有的全部资源，待以后需要时重新申请；或者由系统强行剥夺，但要求被剥夺的资源能够保存与恢复现场（如处理机寄存器与内存可以保存，打印机则不行）。这种方式实现复杂、系统开销大（反复释放与申请可能使前段工作失效），且可能降低系统吞吐量，一般只适用于处理机寄存器和内存这类可保存与恢复的资源。

## 死锁预防：破坏循环等待条件
破坏循环等待条件最常用的方法是资源有序分配法：把系统中的全部资源按类型统一编号（如输入机 1、打印机 2、穿孔机 3 等），规定每个进程必须按编号递增的顺序申请资源，同类资源一次性申请完。这样，若进程已占有编号较大的资源，它就不可能再申请编号较小的资源，因此不可能形成环路等待。该策略资源利用率与吞吐量较高，但限制了资源的申请顺序，可能给用户编程带来不便；此外编号必须相对稳定，新增资源类型时编号的插入会比较麻烦。

## 死锁避免与安全状态
死锁避免不破坏四个必要条件，而是在资源分配时进行判断，只允许不会导致系统进入不安全状态的分配。所谓安全状态，是指系统能按某种进程顺序（安全序列）为每个进程分配其所需的资源，直至所有进程都能顺利完成；安全序列是指这样的进程序列 P1, P2, …, Pn：对每个 Pi，其尚需的资源量不超过当前可用资源加上所有前序进程释放的资源之和。若系统不存在任何安全序列，则处于不安全状态。安全状态一定不会死锁，不安全状态不一定死锁，但可能死锁。因此死锁避免算法保证系统始终处于安全状态。

## 银行家算法
银行家算法是最著名的死锁避免算法，其数据结构包括：Available[j] 表示第 j 类资源的当前可用数量；Max[i][j] 表示进程 i 对第 j 类资源的最大需求；Allocation[i][j] 表示已分配数量；Need[i][j] = Max[i][j] − Allocation[i][j] 表示尚需数量。当进程 i 提出请求 Request[j] 时依次判断：若 Request[j] > Need[i][j] 则出错（请求超过其最大需求）；若 Request[j] > Available[j] 则表示资源不足，进程需等待；否则试探性地分配并修改数据结构，再执行安全性算法检查系统是否仍安全，若安全则正式分配，若不安全则撤销试探分配并让进程等待。

```c
/* 银行家算法：安全性检查 + 资源请求试探分配 */
#define P 5      /* 进程数 */
#define R 3      /* 资源类型数 */

int available[R];              /* 当前可用资源 */
int maxneed[P][R];             /* 各进程最大需求 Max */
int alloc[P][R];               /* 已分配 Allocation */
int need[P][R];                /* 尚需 Need = Max - Allocation */

/* 安全性算法：若存在安全序列则返回 1，并把序列写入 safe[] */
int is_safe(int safe[]) {
    int work[R], finish[P] = {0};
    for (int j = 0; j < R; j++) work[j] = available[j];
    for (int k = 0; k < P; k++) {
        int found = -1;
        for (int i = 0; i < P; i++) {
            if (finish[i]) continue;
            int ok = 1;
            for (int j = 0; j < R; j++)
                if (need[i][j] > work[j]) { ok = 0; break; }
            if (ok) { found = i; break; }        /* 找到可满足的进程 */
        }
        if (found < 0) return 0;                 /* 找不到则系统不安全 */
        for (int j = 0; j < R; j++) work[j] += alloc[found][j];
        finish[found] = 1;
        safe[k] = found;
    }
    return 1;
}

/* 资源请求：进程 p 请求 req[R]，能安全分配返回 1 */
int request(int p, int req[]) {
    for (int j = 0; j < R; j++) {
        if (req[j] > need[p][j]) return 0;       /* 超过最大需求，视为出错 */
        if (req[j] > available[j]) return 0;     /* 资源不足，等待 */
    }
    for (int j = 0; j < R; j++) {                /* 试探性分配 */
        available[j] -= req[j];
        alloc[p][j] += req[j];
        need[p][j]  -= req[j];
    }
    int safe[P];
    if (is_safe(safe)) return 1;                 /* 安全：正式分配 */
    for (int j = 0; j < R; j++) {                /* 不安全：撤销试探分配 */
        available[j] += req[j];
        alloc[p][j] -= req[j];
        need[p][j]  += req[j];
    }
    return 0;
}
```

## 银行家算法示例
设系统有 A、B、C 三类资源，总量分别为 10、5、7。五个进程的 Allocation 为 P0(0,1,0)、P1(2,0,0)、P2(3,0,2)、P3(2,1,1)、P4(0,0,2)，Max 为 P0(7,5,3)、P1(3,2,2)、P2(9,0,2)、P3(2,2,2)、P4(4,3,3)，则 Need 为 P0(7,4,3)、P1(1,2,2)、P2(6,0,0)、P3(0,1,1)、P4(4,3,1)，Available 为 (3,3,2)。此时存在安全序列 P1、P3、P4、P0、P2，系统安全。若 P1 请求 (1,0,2)，试探分配后 Available 变为 (2,3,0)，此时任何进程的 Need 都无法被满足，不存在安全序列，故该请求不能立即满足，应让 P1 等待。

## 死锁检测与解除
死锁检测允许死锁发生，通过定时运行检测算法来发现死锁。检测的数据结构是资源分配图的化简判断，对每类资源多实例的情形，算法维护 Work 与 Finish 向量：反复寻找 Need 不超过 Work 的进程，假设其完成并回收其资源，若最终仍有进程未完成则这些进程处于死锁。解除死锁的常用方法有三种：剥夺资源，从其他进程剥夺足够数量的资源分配给死锁进程，但需考虑被剥夺进程的推进情况，避免其因资源长期不足而饥饿；撤销进程，强制撤销所有死锁进程或按代价（优先级、已运行时间、已占用资源数、是否交互式等）逐个撤销，直至死锁解除；进程回退，让进程回退到足以避免死锁的某个检查点，代价是需保存历史信息。

## 三种策略的比较与选择
死锁预防的优点是简单可靠、无需运行时判断，缺点是资源利用率低、并发度下降，且有的条件（互斥）根本无法破坏。死锁避免的优点是资源利用率较高、不必破坏必要条件，缺点是必须预知每个进程的最大资源需求、算法开销较大、进程之间缺乏灵活性。死锁检测与解除的优点是资源利用率最高、允许并发充分推进，缺点是检测本身需要开销，且解除时要付出撤销或回退的代价。实际系统中常采用混合策略：对内核内部使用的资源（如锁）采用严格的预防措施，对用户作业使用的资源采用检测与解除。
