# 知识图谱说明

> 本次把「知识图谱」从**只看学生个人练习记录的空图**，改造成**完整的课程 → 章节 → 知识点结构图 + 161 条知识点关系**，
> 并把测验、代码练习、掌握度、错题里的知识点名称全部挂到图谱上。

---

## 一、改之前的问题

1. **前端只用一个接口构图**：`KnowledgeGraph.tsx` 原先只读 `/api/profile/knowledge-mastery`（学生自己的练习记录）。
   后端明明已经有 105 个知识点、42 个章节、161 条关系，前端一个都没用。
2. **没有任何章节节点，也没有任何关系边**。
3. **最严重**：练习记录为空时，页面直接 `return` 一个「暂无可绘制的知识图谱」的空状态，**整张图都不画**。
   新学生（或内置账号）进去基本就是一片空白。
4. 后端**其实早就有** `GET /api/knowledge/graph`（组员实现，返回 `nodes` + `edges`），只是前端从没调用过。
5. 关系太少且**只有课程内关系**：`knowledge_point_prerequisites` 表里只有 69 条，全部是同一门课内部的，没有任何跨课程关系。
6. 测验/练习/掌握度里的知识点名称与图谱规范名**两套命名**，互相挂不上（我用图谱节点的「去测验巩固」跳过去，一道题都筛不出来）。

## 二、本次改动

### 1. 关系从 69 条扩到 161 条

| 类型 | 数量 | 含义 |
|---|---|---|
| `prerequisite` | **123** | 课程内前置关系（如「二叉树 ← 树」「快速排序 ← 分治法」） |
| `cross_subject` | **38** | **跨课程关系**（新增能力） |
| 合计 | **161** | 105 个知识点**无一孤立**，全部至少有一条关系 |

跨课程关系覆盖 **8 个课程组合**：

| 关系方向 | 条数 | 例子 |
|---|---|---|
| 操作系统 → 数据结构 | 11 | 处理机调度 ← 队列；文件系统 ← 树；死锁 ← 图 |
| 操作系统 → 计算机组成原理 | 8 | 内存管理 ← 主存储器；虚拟内存 ← 高速缓冲存储器 |
| 数据结构 → C语言 | 7 | 链表 ← 指针；串 ← 字符串与字符数组 |
| 计算机网络 → 数据结构 | 4 | 路由选择 ← Dijkstra 算法；拥塞控制 ← 队列 |
| 操作系统 → C语言 | 3 | 文件系统 ← 文件操作；内存管理 ← 动态内存管理 |
| 计算机网络 → 计算机组成原理 | 2 | 数据链路层 ← 数据的表示（CRC 编码） |
| 计算机组成原理 → C语言 | 2 | 数据的表示 ← 数据类型与变量 |
| 计算机网络 → 操作系统 | 1 | 网络体系结构 ← 进程与线程 |

**注意方向语义**：`A ← B` 表示「A 依赖 B」（B 是 A 的基础），对应表里 `knowledge_point_id = A`、`prerequisite_knowledge_point_id = B`。

### 2. 跨课程关系为什么单独成文

组员的框架里，关系写在每门课的 `data/knowledge-base/<课程>/catalog.json` 的 `relations` 字段，
而 `knowledgePointService.seedKnowledgePoints()` 解析关系时是按**当前课程**取 id 的（`WHERE subject=?`），
**结构上表达不了跨课程关系**。

因此新增一个数据文件 `data/knowledge-base/cross-subject-relations.json`，并在 `knowledgeBootstrapService`
导入流程里一并写入同一张关系表，`relation_type` 用 `cross_subject` 以便与课程内 `prerequisite` 区分
（这样既不影响按 `prerequisite` 做的检索查询扩展，前端又能分层渲染）。

### 3. 补齐 71 条知识点别名（游离名称 69 → 3）

测验、开放题、代码练习、掌握度、错题里共出现 **69 个名称**既不是图谱规范名、也不是已登记别名，例如
「线性表」「红黑树旋转」「顺序表与链表」「进程、线程、调度与上下文切换」「TCP连接建立、数据传输与连接释放」。

新增 `data/knowledge-base/extra-aliases.json`，把这些名称登记为规范知识点的别名（别名数 408 → **479**）。
效果：

| 来源 | 改前命中 | 改后命中 |
|---|---|---|
| 代码练习 code_exercises | 45/50 | **50/50** |
| 掌握度 student_knowledge_mastery | 0/3 | **3/3** |
| 错题 wrong_questions | 0/2 | **2/2** |
| 选择题 question_bank | 15/44 | **43/44** |
| 开放题 open_question_bank | 20/60 | **58/60** |

剩下 3 个确实在图谱里没有对应知识点：「数据结构选择」「性能评价」（没有这个图谱节点）、「Python / 列表可变性」（Python 未建图谱）。

> 「线性表」「栈与队列」「树与二叉树」「图遍历」这类**章节级名称**同时覆盖两个知识点，
> 因此做了双向归属（如「线性表」同时是「数组」和「链表」的别名），避免只挂一边。

### 4. 测验按知识点筛选支持规范名

`questionBankService.listQuestions()` 原先对 `knowledge_point` 做**精确匹配**，
所以从图谱点「去测验巩固」（传的是规范名）会返回 0 题。改为：**精确匹配保留 + 按别名表匹配**。

修好后的实测：

| 传参 | 改前 | 改后 |
|---|---|---|
| 数组（规范名） | 0 ❌ | 4 ✅ |
| 链表（规范名） | 0 ❌ | 4 ✅ |
| 处理机调度（规范名） | 0 ❌ | 4 ✅ |
| 函数（规范名） | 0 ❌ | 4 ✅ |
| 数据的表示（规范名） | 0 ❌ | 9 ✅ |
| 网际协议与子网（规范名） | 0 ❌ | 4 ✅ |
| 线性表（题库原名） | 4 ✅ | 4 ✅（行为不变） |

同时处理了学科名差异（题库用「C 语言程序设计」，知识库用「C语言」）。

### 5. 掌握度接口补出规范知识点名

`student_knowledge_mastery` 表**没有** `knowledge_point_id` 列，只能靠名称关联，
而掌握度存的是测验原始名（如「红黑树旋转」「数据表示」），与图谱节点名（「红黑树」「数据的表示」）不一致 ——
改前**一条都挂不上图谱**。

在 `profileService.listKnowledgeMastery()` 里新增一个字段 `knowledge_point_canonical`（后端按别名表解析），
前端优先用它匹配。实测：未匹配记录从 **2 条降到 0 条**，掌握度正确挂到知识点节点，并向上聚合到章节与课程节点。

> 该字段是**纯新增**，不影响任何既有调用方。

## 五、已知限制

1. **关系是课程级粒度，不是"每章之间"的细粒度连线**。目前 38 条跨课程关系连的是**知识点**，
   前端把它们按所属章节/课程聚合展示（如徽章 `操作系统 → 数据结构 11`）。
   如果需要"章节 A → 章节 B"这种更粗的课际依赖图，现在的折叠视图已经能做到。
2. **`/api/knowledge/graph` 返回的不是数组**（是 `{nodes, edges, resources}` 对象），
   所以前端结构接口用的是 `apiRequest<T>()` 而不是 `fetchApiData<T>()`（后者只在 payload 是数组时取数）。
3. **知识点的 `label` 不是全局唯一**：「数组」同时出现在 C语言 和 数据结构。
   因此前端节点 id 用的是后端数字 id（`knowledge::<id>`），**绝不能拿名称当 key**。
4. 掌握度记录粒度可能比图谱节点粗（如掌握度「红黑树旋转」对应图谱的「红黑树左旋/右旋」两个节点）。
   现在靠别名解析做了归一，但若以后出现新命名，需要在 `extra-aliases.json` 里补一条映射。
5. **开放题库（60 道面试追问）目前没有任何页面展示**：它有 `GET /api/open-questions` 接口，
   但学生端和教师端都还没调用。这是独立的一条功能线，不是本次改动引入的问题。
6. 后端 `/api/knowledge/graph` 由组员实现（`routes/aiLearning.js` + `personalKnowledgeService.getKnowledgeGraph`），
   **本次没有改它的代码**，只是补上了它依赖的关系数据与别名数据。
   我一度加过一个同名的重复接口，发现遮蔽后已撤销，避免出现两份实现。
